# Reference-project review

Reviewed on 2026-10-30. This is a targeted comparison of relevant source files and documented architecture, not an exhaustive audit of these external projects. No external implementation was copied into the application. These references inform design; they do not prove e-Hailer's behavior or security.

| Reference and inspected source | Applicable lesson | e-Hailer decision |
| --- | --- | --- |
| [courierManagementSystem: courier model](https://github.com/whattadarsh/courierManagementSystem/blob/3989ac85e551a982d81045e6387749af53993826/lib/core/models/courier_model.dart) | Courier quantity, dimensions, physical weight, origin/destination and delivery milestones belong in an explicit model. | Preserve those inputs in manual domain entities. Calculate billable weight and fare on the server. The inspected model does **not** establish an IATA divisor or a secure settlement system; the `/5000` tariff is this project's explicit policy. |
| [myoga: payment choices](https://github.com/softontechsolution/myoga/blob/ef35cafd5d10e796d54059a3b707ea1221d45695/lib/services/views/Payment_Methods/payment_methods_screen.dart) | Present familiar courier/payment choices clearly. The inspected screen includes fixed display prices. | Use actual pickup/drop-off inputs, a trusted road quote and a review step. A displayed price or payment selection never establishes that money was received. |
| [Deliverzler: responsive layout](https://github.com/AhmedLSayed9/deliverzler/blob/644ee68715c7ec701dfa4ed59ecfb3eb167ec88b/lib/core/presentation/widgets/responsive_widgets/responsive_layouts.dart) and [bounded content](https://github.com/AhmedLSayed9/deliverzler/blob/644ee68715c7ec701dfa4ed59ecfb3eb167ec88b/lib/core/presentation/widgets/responsive_widgets/responsive_center.dart) | Width classes and bounded content avoid stretching phone layouts across desktop windows. | Shared 600/840 breakpoints, maximum content widths and columns that stack for narrow windows or large text. Keep e-Hailer's manual models instead of importing the reference's generated-model workflow. |
| [Fleetbase architecture/README](https://github.com/fleetbase/fleetbase#readme) | Modular logistics capabilities have distinct operational responsibilities, with an API separate from the console. | Keep delivery, wallet, disputes and operations boundaries explicit. Do not import its PHP/Ember deployment or claim its extensions exist here. This comparison is architecture-level, not a review of FleetOps dispatch internals. |
| [ERPNext: payment entry](https://github.com/frappe/erpnext/blob/develop/erpnext/accounts/doctype/payment_entry/payment_entry.py), `validate` and `on_submit` | Validate references, amounts and duplicates before posting ledger effects; reconcile outstanding amounts. | Server-owned receipts, integer minor-unit arithmetic, atomic ledger/balance updates and bounded refunds. This is not a complete accounting ledger or ERPNext integration. |
| [osTicket: ticket assignment](https://github.com/osTicket/osTicket/blob/develop/include/class.ticket.php), `assignToStaff` | Assignment checks staff availability and records an event; ticket state and responsibility should remain traceable. | Authorize support/admin actions and write dispute audit events. Support cannot issue refunds; the financial command requires admin authority. |

The original Antigravity conversation (`a9cac416-ba4e-4f49-a54b-9b590e8b691f`) supplied the design context. Its completion claims were checked against the repository and tests. Historical suggestions involving Google Maps billing, generated Flutter models, fake top-ups or client-authorized PIN/financial writes are not the current implementation.
